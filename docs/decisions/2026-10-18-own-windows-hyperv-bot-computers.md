# 2026-10-18 — Own Windows Hyper-V Bot computers

- **Context:** Local Bot computer setup only implemented Linux KVM. Windows users need the same separate, persistent guest without giving Gbot control of their Windows desktop. Arch signed this adapter boundary on 18 October at 09:37 UTC.
- **Decision:** Add a Windows PowerShell 5.1 Hyper-V adapter behind the existing Workspace setup, SSH, desktop and task lifecycle. Read-only preflight checks Windows edition, virtualization, Hyper-V availability, restart requirements, permissions, resources and free disk space. GChat never enables Windows features, elevates, restarts the host or installs host packages; the user completes any required Windows Features step and reboot.
- **Ownership:** Each guest has an exact workspace name, generated Hyper-V VM identifier, ownership note, persistent directory, disk, seed and COM pipe. Mutations recheck those claims and refuse foreign or ambiguous registrations. Interrupted setup retries retain identity. Retire deletes only the claimed guest; stop preserves its disk, brain, vault key and connected accounts, fences unfinished tasks/schedules and human control, and waits for graceful shutdown without an automatic forced power-off.
- **Storage and transport:** Select a fixed non-system drive with sufficient free space when available and persist its root; subsequent starts never move the guest. Reuse the existing Default Switch without changing host networking. Use the same pinned Debian image and worker archives as KVM, convert the image with an existing image tool, and build the cloud-init ISO through Windows IMAPI2. The guest is Generation 2 with guest Secure Boot disabled to support its COM console pipe. This changes the owned guest only. Capture its SSH host key through that pipe before connecting; never trust an observed network key. A loopback-only SSH relay resolves the owned guest's current IP on each connection, retaining the saved endpoint and vault-backed key across guest restarts. The existing readiness check still proves files, commands, capture, input and media before admitting tasks.
- **Consequences:** New platform-neutral local-VM API routes coexist with the existing KVM routes. Contract tests and a fake PowerShell Hyper-V module cover the adapter without enabling features or creating a native VM. Native acceptance remains pending on Ron's Windows 11 Pro .143 host after his Hyper-V enable-and-reboot step; source tests do not qualify a live Windows guest.
